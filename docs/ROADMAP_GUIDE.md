# ロードマップの書き方

`data/roadmap.yaml` がロードマップの単一の信頼できる情報源。
`dist/roadmap.html`（ガントチャート＋トラック別タイムライン）と `PROFILE.md` はここから生成される。

## 目標との関係

| | 目標（`data/goals.yaml`） | ロードマップ（`data/roadmap.yaml`） |
|---|---|---|
| 問い | 何を達成したいか | いつ、どの順番でやるか |
| 期間 | 四半期 | 数ヶ月〜1 年 |
| 単位 | Objective / Key Result | トラック / マイルストーン |
| 変更頻度 | 四半期ごと | 月次の棚卸しで随時 |

目標は「向き」、ロードマップは「経路」。
マイルストーンの `goals` に目標 ID を書くと双方向に辿れるようになり、
`pnpm validate` で存在しない目標への紐付けが検出される。
検証はロードマップの読み込み中ではなく、全ファイルを読み終えたあとに行う
（`RoadmapModel.referencedGoalIds` × `GoalsModel.ids`）。
こうしておくと `goals.yaml` が壊れていても `roadmap.yaml` 側のエラーが同時に見える。

**目標に紐付かないマイルストーンがあってよい**（土台づくりや興味駆動の学習）。
ただし紐付かないものが半分を超えたら、目標の側が実態を表せていない合図。

## トラックの切り方

トラックは「並行して伸ばす軸」。**3〜4 本に絞る**。
増やすほど「全部やる」計画に近づき、どれも進まなくなる。

良い切り方:

- **成果の出方が違うもの同士**で分ける（インフラ / 設計力 / 発信）
- 1 本は**今の仕事で必ず使う軸**にする（進捗が自然に出る）
- 1 本は**仕事では強制されない軸**にする（発信・育成など、やらないと何も起きないもの）

避ける切り方:

- 技術スタック単位（`terraform` / `kubernetes`）… スキル一覧と二重管理になる。技術は `skills` で表す
- 時間単位（短期 / 長期）… `start` と `due` があるので冗長
- 粒度のばらばらな寄せ集め

## マイルストーンの粒度

**1〜3 ヶ月で終わる塊**にする。

- 短すぎる（1〜2 週）→ それは `steps` の 1 行。マイルストーンにすると一覧が TODO リストになる
- 長すぎる（半年以上）→ 途中の状態が見えず、進捗が 0% のまま数ヶ月が過ぎる。分割する

目安として `steps` が 3〜6 個に収まる大きさがちょうどいい。
進捗は `steps` の完了率で計算されるので、`steps` が 1 個だと進捗が 0% か 100% しか取らない。

## `outcome` の書き方

`outcome` は「何ができたら終わりか」の定義。
これが曖昧だと、終わったかどうかを後から自分に都合よく判定してしまう。

- **状態**で書く（「〜できている」「〜が残っている」）。作業（「〜をやる」）で書かない
- 第三者が確認できる形にする（成果物・記録・実演のいずれかが残る）
- 2〜3 文に収める。長い場合はマイルストーンが大きすぎる

| 悪い例 | 直した例 |
|---|---|
| Terraform を整備する | VPC / RDS / ECS がモジュール経由で記述され、本番とステージングが同じモジュールの異なる変数で表現されている。plan の差分がゼロで安定する |
| k8s に慣れる | 本番の Pod 異常・ノード障害に手順を見ずに一次対応できる。対応記録がポストモーテムとして残っている |

## 依存関係の扱い

`depends_on` には「**先に終わっていないと着手しても無駄になるもの**」だけを書く。
「あった方が楽」程度の関係を書くと、全部が一直線に並んで並行して進められなくなる。

- 存在しないマイルストーン ID、自己依存、循環依存（a → b → a）はスキーマエラーになる
- 未完了の依存は「ブロッカー」として HTML に表示される（`.badge--warn` の「待ち」）
- 自分が `done` ならブロッカーは表示されない。終わったものに「待ち」は無く、
  出すと「手当てが必要なマイルストーン」に完了済みが並んで一覧が信用できなくなる
  （依存先の `status` を直し忘れただけ、というケースがほとんど）

### `status: blocked` と `blocked_reason`

自分の努力では進められない状態は `planned`（まだ着手しない）と区別して `blocked` にする。
`blocked` には `blocked_reason` が必須（スキーマで強制）。理由のない `blocked` は
そのまま放置されるだけで、何の行動にもつながらないため。

`blocked_reason` には「**誰の・何が解決すれば動けるのか**」を書く。
書けないなら、それはブロックではなく自分が着手していないだけ。

## 月次の棚卸し

1. `steps` の `done` を実績に合わせる
2. `pnpm build` して `dist/roadmap.html` の「手当てが必要なマイルストーン」を見る
   - サマリのバーは**完了率**（`done / total`）で、大きな数字「N/M」と分母が一致する。
     ステップまで含めた**平均進捗**はバーの下に数字で添える（分母が違う別の指標なので重ねない）
   - **遅延**（`due` を過ぎて未完了）→ 期限を引き直すか、縮小するか、落とす
   - **ブロック中** → `blocked_reason` がまだ有効か確認する。解消していたら status を戻す
   - **依存待ち** → 依存元を先に進めるか、依存を切れないか考える
3. ガントチャートで翌月に 3 本以上のバーが重なっていたら、どれかを後ろにずらす

期限を過ぎた項目を放置して更新しないのが一番よくない状態。
計画が外れたら、外れた事実（新しい `due`）を書く。

## 検証

```bash
pnpm validate   # スキーマ + スキル ID / 目標 ID の参照整合性
pnpm build      # dist/ と PROFILE.md を再生成
```

スキーマ（`src/schema/roadmap.ts`）が弾くもの:

- `id` が kebab-case でない / 重複している
- `start > due`
- `tracks` に存在しない `track` の参照
- 存在しない `depends_on`・自己依存・循環依存
- `status` が `planned` / `in_progress` / `done` / `blocked` 以外
- `blocked` なのに `blocked_reason` がない
- 未知のキー（`dependsOn` のようなタイポ）

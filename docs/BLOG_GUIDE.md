# ブログ執筆ガイド

このリポジトリのブログは「読まれるため」だけでなく **スキルの裏付けを残すため** にある。
`blog/posts/*.md` が単一の信頼できる情報源で、`dist/blog/` と `PROFILE.md` のブログ節は `pnpm build` の生成物。
生成物は手で編集しない。

## 1. 記事を作る

```bash
pnpm growth new-post "Terraform の state を壊して復旧した" \
  --slug terraform-state-recovery \
  --skills infra-terraform,cloud-aws \
  --tags terraform,aws
```

| オプション | 意味 |
|---|---|
| `--slug <slug>` | ファイル名・URL に使う kebab-case の識別子。省略時はタイトルから生成する |
| `--skills <id,...>` | **必須**。`data/skills.yaml` のスキル ID |
| `--tags <tag,...>` | タグ。省略時は `--skills` と同じ値が入るので、あとで記事の内容に合わせて直す |
| `--date <YYYY-MM-DD>` | 記事の日付。省略時は今日（JST） |
| `--draft` | `blog/drafts/` に作る（サイトには出力されない） |

日本語だけのタイトルからは slug を生成できない（英数字が残らない）。
その場合はエラーになるので `--slug` を明示する。ローマ字への自動変換はしない
— 誤変換した slug は URL として半永久的に残ってしまうため、人間が決める。

同名のファイルが既にあるときは上書きせずエラーにする。書きかけの記事を失わないためのガード。

## 2. ファイル名と置き場所

```
blog/posts/YYYY-MM-DD-slug.md    公開記事（サイトに出力される）
blog/drafts/YYYY-MM-DD-slug.md   下書き（出力されないが、本数はダッシュボードに出る）
```

- ファイル名の日付と front matter の `date` は**必ず一致**させる。食い違うとビルドが失敗する
  （一覧の並び順とページの表示日がずれる＝データの腐敗を放置しないため）。
- 日付を変えるときはファイル名もリネームする。
- 存在しない日付（`2026-02-30` など）はエラーになる。
- ファイル名の slug とタイトルの不一致は許容する。タイトルは読者向け、slug は URL 向けで役割が違う。

### 公開記事に未来日は置けない

`status: published` の記事の `date` が今日（JST）より後ならビルドが失敗する。
予約投稿の仕組みはこのリポジトリに無いため、未来日は `date` の書き間違いである可能性が高い。
黙って丸めると「最終投稿から -3 日」のような表示になり、間違った日付が一覧の並び順と
投稿ペースの集計に残り続ける（＝データの誤りが隠れる）ので、明示的に失敗させている。

執筆予定日として未来日を使いたいときは `status: draft`（または `blog/drafts/`）にする。
下書きの未来日は許容され、投稿ペースの集計対象にも入らない。

## 3. front matter

```yaml
---
title: Terraform の state をロックごと壊して復旧するまで
date: 2026-09-20
tags: [terraform, aws, troubleshooting]
skills: [infra-terraform, cloud-aws, infra-cicd]
summary: CI の同時実行で state が壊れ、import と state rm で復旧した記録。
status: published
---
```

| フィールド | 必須 | 意味と制約 |
|---|---|---|
| `title` | ○ | 記事タイトル。`:` や引用符を含んでもよい（`new-post` が YAML として安全に埋める） |
| `date` | ○ | `YYYY-MM-DD`。一覧の並び順・投稿ペースの集計に使う。ファイル名の日付と一致させる。`status: published` では**未来日にできない**（後述） |
| `tags` | ○ | 1〜8 個の kebab-case。記事の分類。表記揺れを防ぐため大文字・アンダースコアは不可 |
| `skills` | ○ | 1〜8 個の kebab-case。`data/skills.yaml` の `id`。存在しない ID はビルドで失敗する |
| `summary` | ○ | 10 文字以上。一覧・ダッシュボードのカード・`PROFILE.md` に出る。本文の結論を 1〜2 文で |
| `status` | ○ | `published` または `draft`。省略不可（書き忘れが意図せぬ公開になるのを避けるため） |
| `links` | — | 参考資料。`{ label, url }` の配列。記事末尾に「参考」として出力される |

未知のフィールドはエラーになる。`tag:` のようなタイポが黙って無視され、
「書いたはずのタグが反映されない」状態になるのを防ぐためにスキーマを strict にしている。

### `skills` を書く意図

`skills` はスキル棚卸し（`data/skills.yaml`）との結線である。

- 「このスキルはレベル 3」と主張する**根拠**が記事として残る。
- 逆に、記事が 1 本もないスキルは自己評価が高すぎる可能性が高い、というシグナルになる。
- `pnpm validate` / `pnpm build` は `skills` の ID が `data/skills.yaml` に存在するかを検証する。
  タイポした ID は「紐付いているように見えて紐付いていない」最悪の状態なので、必ず失敗させる。

記事を書き終えたら、`data/skills.yaml` の該当スキルの `evidence` や `level` を見直すのが本来の往復。

## 4. 本文の構成: 課題 → 試したこと → 原因 → 学び

テンプレート（`templates/blog-post.md`）はこの 4 節で固定している。
感想文ではなく**再現できる記録**にするための型。

| 節 | 書くこと | 避けること |
|---|---|---|
| 課題 | 前提の環境、エラーメッセージ、再現手順 | 「うまく動かなかった」だけの要約 |
| 試したこと | 仮説と検証を時系列で。**失敗した試行も残す** | 成功した手順だけの清書 |
| 原因 | 根本原因。断定できなければ「推測」と明記し、確かめる方法も書く | エラー抑制で済ませた記録 |
| 学び | 次に同じ場面で最初にやること。`skills` と対応させる | 一般論・教科書的なまとめ |

書き方の実務的なコツ:

- **コードブロックには言語を指定する**（` ```bash `, ` ```yaml `）。`.prose` のスタイルが効く。
- 表・箇条書き・引用は積極的に使う。構造があるほど半年後の自分が読み返しやすい。
- 読了時間は本文から自動計算する（日本語 400 字/分・英語 200 語/分、コードブロックは除外）。
  手で書く必要はない。

## 5. 下書きの運用

- 書き始めは `--draft` で `blog/drafts/` に置く。サイトには出力されないが、
  **下書き本数はダッシュボードに出る**（書きかけを可視化して、放置を自覚するため）。
- 公開するときは `blog/posts/` に移動し、`status: published` に変える。
- `blog/posts/` に置いたまま `status: draft` にしても非公開になる。レビュー待ちの記事に使う。
- 下書きでも `skills` の参照整合性は検証される。公開時に初めて壊れていると気付くのは遅すぎる。
- 下書きは `date` を未来日にできる（「この日までに書く」という予定として使える）。
  公開に切り替えるときは、実際の公開日に `date` とファイル名を直す。

## 6. 確認する

```bash
pnpm validate   # front matter・ファイル名・スキル ID 参照をすべて検証
pnpm build      # dist/blog/ と PROFILE.md を生成
pnpm test       # 集計・レンダラの振る舞いを検証
```

1 記事でもパースに失敗すればビルド全体が失敗する（壊れた記事を黙って skip しない）。
エラーメッセージには必ずファイル名と原因が入るので、そこから直す。

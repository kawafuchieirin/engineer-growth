# 実績（バッジ）とクエスト

実績の定義は `src/lib/achievements.ts`、クエストの算出は `src/lib/quests.ts` にある。
XP の計算規則の正は `docs/GAME_DESIGN.md`。この文書は「どんな実績があり、なぜあるのか」を説明する。

## なぜ実績があるのか

スキル棚卸しは、続けていると「何も変わっていない」ように見える。
レベル 2 のスキルを 3 に上げるには数ヶ月かかるし、記事を 1 本書いても一覧に 1 行増えるだけで、
次の棚卸しまでに何を積んだのかが思い出せない。

実績は、その**積み上がりに名前を付けて見えるようにする**ための仕組みである。
未解放のものも進捗付きで表示するのは、「次に何を取りに行けるか」を目標として機能させるため。
だから進捗 0.88 の「底上げ」は、解放済みの実績より価値のある表示になる。

### 盛れないこと

実績の解放状態は `data/*.yaml` と `blog/posts/` から導出するだけで、**どこにも保存しない**。
`data/history.yaml` に残るのは「その日時点で解放されていた id」の記録だけで、
そこに id を書き足しても次のビルドで上書きされる。

解放する唯一の方法は、実際にスキルを上げる・KR を進める・記事を書くこと。
この制約がないと、落ち込んだ日に数字をいじって気分を良くする道具になり、
「成長している」という感覚だけが残って成長が止まる。

### 「成した」ことだけを実績にする

`docs/GAME_DESIGN.md` の末尾にあるとおり、この仕組みが壊れるのは
**実績の条件が実力と無関係になったとき**である。

- 実績になる: 「記事を 25 本公開した」「依存のあるマイルストーンを順番に完了した」
- 実績にしない: 「ログインした」「ファイルを開いた」「7 日連続でサイトを見た」

後者は回数を稼げば誰でも取れるので、取っても何も証明しない。
バッジが並ぶ気持ちよさだけが残り、「バッジが多い自分」と「実力のある自分」が乖離していく。

ただし **行動の継続は実績にする**（4 週連続投稿など）。継続は結果を生む行動そのもので、
「サイトを開いた」のような計測のためだけの行動とは違う。

### 失敗も実績にする

`retrospective-on-dropped`（やめた理由を残す）は、取りやめた目標に振り返りを書くと解放される。
取りやめは失敗ではなく判断であり、その判断の理由を残せたことは成果である。
これを実績にしないと「やめたら負け」になり、終わらない目標を抱え続ける動機が生まれる。
同じ理由で、達成率の分母からも `dropped` は外している（`src/lib/goals.ts`）。

### 条件の細かい解釈

一覧の条件だけでは判断が分かれるところを、実装がどう決めているか書いておく。

- **`category-all-self-reliant`** — 対象はスキルが 1 件以上登録されたカテゴリのみ。
  空のカテゴリを「0 件中 0 件が達成」と数えると、スキルを 1 つも書いていないだけで解放されてしまう。
  進捗は最も達成に近いカテゴリの比率で見せる。
- **`quarter-clean-sweep`** — 分母は `dropped` を除いた件数（`src/lib/goals.ts` の達成率と同じ集合）。
  進捗は最も達成に近い四半期の比率。
- **`key-results-ten`** — `current >= target` に到達した KR の数。超過達成は 1 件として数える。
- **`dependency-chain-cleared`** — `depends_on` を持つマイルストーンが `done` で、
  かつその依存先すべてが `done` であること。順番を飛ばして閉じたものは数えない。
- **`no-untouched-skill`** — 「登録した全スキル」が分母なので、スキルを増やすと一度は未達に戻る。
  これは正しい挙動で、「まだ触っていない技術を書き出した」状態を未達として扱う。
- **`history-ten-records`** — 件数は `data/history.yaml` の記録数。
  集約側が件数を渡さない場合は 0 件として扱う（履歴を読む前でも実績を評価できるようにするため）。

## 表示の並び順

`tier 昇順 → 解放済みを先 → 進捗の降順 → id 昇順`。

tier を昇順にするのは、手が届く範囲を上に置くため（platinum を先頭にしても
「遠すぎて関係ない」と読み飛ばされる）。同じ tier では解放済みを先に置いて積み上げたものを見せ、
その次を進捗の降順にすると「あと一歩」が未解放の先頭に来る。
最後の id 昇順は出力を決定的にするための同値解消（データが変わらなければ再ビルドで差分が出てはいけない）。

未解放の進捗は小数 2 桁に**切り捨てる**。99.6% を `1.00` と表示すると
「100% なのに未解放」という読めない状態になるため。

## クエスト（次の一手）との関係

クエストは最大 5 件、`urgency`（`now` → `soon` → `later`）の順に、同じ緊急度なら XP の降順で並ぶ。
生成元は次の 6 つで、それぞれ独立した純粋関数になっている。

| 生成元 | urgency | XP の見込み | 編集先 |
|---|---|---|---|
| 遅れているマイルストーンの残りステップ | `now` | ステップ 1 つ = 15 | `data/roadmap.yaml` |
| 30 日以内に期限が来るマイルストーン | `soon` | ステップ 1 つ = 15 | `data/roadmap.yaml` |
| 進捗の遅い Key Result（期末が近い目標） | `soon` | `20 × (1 - 現在の進捗)` | `data/goals.yaml` |
| 途切れそうなストリーク | `now` | 記事 1 本 = 50 | `blog/posts/` |
| データ品質の警告 | `soon` | 0（解消自体に XP の規則はない） | `data/skills.yaml` / `data/goals.yaml` |
| ギャップの大きいスキル | `later` | 累積 XP 表の差分 | `data/skills.yaml` |
| あと一歩の実績（進捗 0.7 以上） | `later` | その実績の XP | 実績ごとの編集先 |

XP の見込みは `src/lib/xp.ts` の係数をそのまま使う。
同じ数字を 2 箇所に書くと、片方だけ直したときにクエストが嘘の見込みを表示する。

クエストが 0 件になることもある。空の一覧は「今やるべきことがない」という正しい情報なので、
枠を埋めるために意味のないクエストは作らない。

### なぜ「なぜ今か」が必須なのか

納得できない指示は無視される。無視されるクエストが並んだ一覧は、次からは読まれない。
だから `why` には具体的な事実（期限までの日数、ステップの消化数、KR の実数）だけを書く。
「がんばりましょう」のような文を入れた時点で、この一覧は読む価値を失う。

同じ理由で、一手を**最大 5 件**に絞っている。10 件並べると「やらないことリスト」になる。

### 同じ対象に 2 つのクエストを出さない

クエストの `id` は対象（マイルストーン id・目標 id・スキル id など）から組み立てている。
`id` の重複はそのまま「同じ対象への二重提示」を意味するので、`id` で重複排除する。
たとえば未完了のステップが 3 つ残っているマイルストーンでも、クエストは 1 件（「残りを 1 つ終わらせる」）。

未完了の依存先を持つマイルストーンはクエストにしない。着手しても進められないので
「次の一手」にならず、並べておくと毎回同じ項目が残って一覧そのものが信用されなくなる。

## 実績を追加・変更するときの指針

### id は改名しない

**`id` は `data/history.yaml` の `achievements` に保存される。**
後から改名すると過去の記録と結び付かなくなり、「いつ解放したか」「この 90 日で何が増えたか」
という差分（`docs/GAME_DESIGN.md`「成長の差分」）が壊れる。
改名前の id は永久に「解放済みだが定義のない実績」として履歴に残り続ける。

- `name` / `description` / `icon` / `tier` / `xp` は自由に直してよい（履歴に入らない）
- `id` は一度決めたら変えない
- 不要になった実績は定義ごと削除する。**削除した id を別の実績で再利用しない**
  （過去の記録が別の意味に読み替わる）

### 追加の手順

1. `src/lib/achievements.ts` の `RULES` に定義と判定関数（`measure`）を 1 件足す。
   判定は個別の純粋関数として書く。`evaluateAchievements` の中に if を並べると、
   定義と条件が別々の場所に散り、実績を 1 つ足すたびに 2 箇所を直すことになる。
2. `measure` は進捗（0-1）と `detail` を返す。件数系は `towards()` を使えば
   「3 / 10 記事（あと 7 記事）」が自動で付く。未解放のものも一覧に出すので、
   「条件を満たしていない」だけでは次の行動が決まらない。
3. `quest` に編集先（`kind` と `target`）を書く。「あと一歩の実績」のクエストがここを使う。
   クエスト側が id の文字列から領域を推測しないで済むよう、条件と同じ場所に置いている。
4. `tests/achievements.test.ts` に「条件を満たすと解放される」ケースを足す。
   `completeInput()` は全実績が解放される状態なので、新しい実績の条件もここに足す。
5. この文書の一覧表を更新する。

### 追加していいか迷ったときの問い

- それは**何かを成した**ことか。回数を稼ぐだけで取れないか
- 条件を満たした自分は、満たす前の自分より**実際に何かができる**ようになっているか
- 未解放のときに「あと何をすればいいか」を `detail` で言えるか

3 つすべてに「はい」と答えられないなら、その実績は作らない。

# 目標（OKR）の書き方

`data/goals.yaml` が目標の単一の信頼できる情報源。HTML（`dist/goals.html`）と
`PROFILE.md` の目標セクションはここから生成されるので、**生成物ではなく YAML を直す**。

## Objective と Key Result の書き分け

| | Objective | Key Result |
|---|---|---|
| 役割 | 向き（どこへ行きたいか） | 距離（どこまで来たか） |
| 性質 | 定性的・記憶に残る一文 | 定量的・数えられる |
| 数 | 1 目標に 1 つ | 1 目標に 2〜4 つ |
| 例 | 手順書に頼らず、インフラをコードから再現できる状態にする | 本番が参照する自作モジュール 3 個 |

Objective に数字を入れない。「Terraform を 3 個書く」は Objective ではなく手段で、
達成しても「で、何ができるようになったのか」が残らない。
逆に Key Result に「〜を理解する」と書かない。理解は外から見えないので判定できない。

### 良い Objective の条件

- 達成した自分を想像できる（状態として書かれている）
- 四半期の終わりに他人へ一文で説明できる
- `horizon.vision` に一歩近づく方向を向いている

### 悪い Key Result の直し方

| 悪い例 | なぜ駄目か | 直した例 |
|---|---|---|
| Kubernetes を理解する | 判定できない | 障害訓練で一次対応できたシナリオ数 4 件 |
| できる限り記事を書く | 目標値がない | 公開記事数 6 本 |
| チームの生産性を上げる | 自分で動かせない | レビュー待ち中央値 1 営業日以内を 8 週 |
| タスクを全部終わらせる | 成果ではなく作業量 | 廃止できた手順書 5 件 |

## measurable にする方法

Key Result は `metric`（何を数えるか）・`target`（いくつにするか）・`current`（今いくつか）の
3 点が揃って初めて進捗になる。数えにくいものは次の順で考える。

1. **成果物の数** — 記事、モジュール、廃止できた手順書
2. **できた回数** — 自力でのデプロイ、一次対応したシナリオ
3. **連続性** — 「差分ゼロを確認できた週」のように、状態を期間で数える
4. **代理指標** — 直接測れないものは、相関する観測可能な数に置き換える（置き換えた理由を `why` に書く）

進捗は `min(current / target, 1)` で計算され、目標の進捗はその平均になる。
つまり **KR の数が多いほど 1 本あたりの重みが下がる**。重みを変えたい場合は KR を分けるのではなく、
別の目標に切り出す方が意図が明確になる。

`status: done` の目標は数値に関係なく進捗 100% として扱う。数字が追いついていなくても
「達成した」という人間の判断を正とするため（数字は判断を助ける道具で、判断そのものではない）。

### 達成率と件数は分母が違う

生成物に並ぶ 2 つの数字は集計スコープが別で、混ぜて読むと実態を誤る。

| 表示 | 対象 | 分母 |
|---|---|---|
| 「2026-Q4 の達成率（対象 N 件 / 達成 M 件）」 | 現四半期のみ | その四半期の `dropped` 以外 |
| 「全四半期の目標（達成 … ・ 取りやめ …）」 | 全四半期・全 status | 全件 |

モデル側も `stats.focus`（現四半期）と `stats.all`（全件）に分かれている（`src/lib/goals.ts`）。
新しい表示を足すときは、どちらのスコープかをラベルに必ず書く。

## `why` を必須にしている理由

四半期の途中で必ず「これ以上やる意味があるか」という判断が発生する。
そのときに判断の軸が無いと、**着手済みであることを理由に惰性で続けてしまう**。

`why` は未来の自分への申し送りで、次の 2 つに答えられる形で書く。

- これをやらなかったら何が起きるのか
- 他の候補より先にやる理由は何か

実際に `data/goals.yaml` の `g-2026q4-perf` は、`why` に書いた優先順位を根拠に
`dropped`（取りやめ）へ移している。取りやめは失敗ではなく判断の結果なので、
達成率の分母からは除外される（`src/lib/goals.ts` の `overallProgress`）。

## 「要注意」と「期間終了」の違い

生成物には 2 種類の注意表示が出る。**促したい行動が違うので分けている**。

| 表示 | 条件 | 促す行動 |
|---|---|---|
| 要注意（at-risk） | 未確定 ＋ **期中** ＋ 期末まで 30 日以内 ＋ 進捗 50% 未満 | やり切る / 目標値を下げる / 取りやめる |
| 期間終了（stale） | 未確定 ＋ **期末を過ぎている** | `done` / `dropped` に確定させ `retrospective` を書く |

期末を過ぎた未完了を at-risk に含めない理由は、終わった四半期に「やり切る」という
選択肢が存在しないため。含めてしまうと過去の目標が永久に要注意として残り続け、
一覧そのものが読まれなくなる（判定は `isAtRisk` / `isStale`。期末当日はまだ期中として扱う）。

## 四半期の回し方

### 1. 策定（四半期の初日まで）

- `horizon.vision` を読み直す。ずれていたら先に vision を直す
- 目標は **3〜4 個まで**。5 個以上は「全部やる」という宣言で、優先順位の放棄
- 各目標に `why` と Key Result を書く。`current` は策定時点の実績を入れる（0 でなくてよい）
- `status: not_started` で開始し、`data/roadmap.yaml` のマイルストーンと紐付ける

### 2. 中間レビュー（期の半分、だいたい 6 週目）

- `current` を実績で更新して `pnpm build` する
- `dist/goals.html` の「要注意の目標」を見る。残り 1 ヶ月で進捗 50% 未満なら警告が出る
  （しきい値は `AT_RISK_WITHIN_DAYS` / `AT_RISK_PROGRESS_BELOW`）
- 警告が出た目標は **やり切る / 目標値を下げる / 取りやめる** のどれかを決める。
  判断は `why` を根拠に行い、決めたことを `retrospective` に書く

### 3. 振り返り（四半期の最終週）

- `current` を最終実績で更新し、`status` を `done` / `dropped` に確定させる
- `retrospective` に「何が効いたか」と「次にどう変えるか」を書く。感想ではなく次の行動の材料にする
- 確定し忘れると「期間が終わった未確定の目標」に残り続ける。そこが空であることが期の締めの合図
- `templates/quarterly-review.md` をコピーして振り返りを記録し、次の四半期の目標を起草する

## 検証

```bash
pnpm validate   # スキーマ + スキル ID の参照整合性
pnpm build      # dist/ と PROFILE.md を再生成
```

スキーマ（`src/schema/goals.ts`）が弾くもの:

- `id` が kebab-case でない / ファイル内で重複している（KR の `id` は目標内で一意）
- `target` が 0 以下、`current` が負数
- `status` が `not_started` / `in_progress` / `done` / `dropped` 以外
- `why` や `metric` の欠落、未知のキー（`quater` のようなタイポ）
- `skills` が `data/skills.yaml` に存在しないスキル ID を指している（`pnpm validate`）

追えるよう、使った材料と判定基準、そして反映できていないものを残しておく。

## レベルの付け方

`data/levels.yaml` の定義に素直に当てた。特に境界は次のように扱った。

- **3（自走）** … 設計から実装・デプロイまで一人で完遂した実物がある。
  個人プロジェクトであっても、動いていて、設計判断の理由を説明できていれば 3 とした。
- **4（牽引）** … 技術選定を主導し、他者をレビュー・育成した証跡が必要。
  公開リポジトリは原則として単独開発なので、ほとんどのスキルは 4 に届かない判定になった。
  これは実力の不足ではなく、**単独開発では証明できない種類の水準**だという意味。
- **1（入門）** … 学習の痕跡はあるが、作って動かした証跡がない。
  ネットワークと Google Cloud がここに該当する（どちらも計画とノートは厚い）。
- **0（未経験）** … 痕跡がまったくない。Kubernetes のみ。

## 反映できていないもの（重要）

1. **業務での経験が一切入っていない。**
   GitHub からは職務の成果が見えない。「インフラエンジニア」という肩書きに対して
   Linux・ネットワーク・監視・障害対応のレベルが低く出ているのは、その分が
   抜けているから。該当するスキルの notes に「要確認」と書いてある。

2. **AI 協働の寄与を切り分けていない。**
   公開リポジトリのコミットは大半が AI 協働（gcp-cert-master 22/25、life-repo 14/18）。
   そのため初版のレベルは「**設計を説明でき、動くものを出し、運用に乗せられた**」
   という水準で付けている。自力で書く速度や、補助なしで同じ設計に到達できるかは
   別の軸であり、本人以外には判定できない。

   なお、ここを理由にレベルを一律に割り引くことはしなかった。理由は 2 つある。
   - 設計判断の理由がコードコメントとして残っており、読んで追える状態になっている。
     借り物の実装を貼っただけでは、この痕跡は残らない。
   - 「どこを AI に任せ、どこを自分で決めるか」の設計自体が成果物になっている
     （`prac-ai-collaboration`）。これは隠す欠点ではなく、記録する能力として扱った。

3. **公開リポジトリの外は見ていない。** private リポジトリ、業務のコード、
   社内のドキュメント、勉強会の実際の運営規模は対象外。

4. **初版は HEAD しか見ておらず、対象の選び方も誤っていた（2026-10-12 に訂正）。**
   `RaiseTech_kadaiyou_repo` を「空」と判定して除外したが、71 コミットあり、
   CloudFormation で VPC・ALB・RDS・EC2 を構築した履歴が残っていた。
   ファイルは後のコミットで削除されており、HEAD だけ見ると存在しない。
   この結果 `infra-network` を 1、`be-database` の notes を「RDBMS の経験なし」と
   誤って記録していた。`history.sh` を新設し、レベル 0-1 を付ける前に
   git 履歴を検索する手順を加えた。

   **教訓**: 「測定された不在」は、測る場所とパターンが正しいときだけ根拠になる。

## 自分で見直すときの手順

1. `notes` に「要確認」が付いた行から始める。GitHub に根拠が無いだけで、
   実際にはできることが入っている可能性が高い。
2. レベルを上げるときは `evidence` に具体物を足す。
   「経験がある」ではなく「何をどこまでやったか」を書く。
   レベル 3 以上で `evidence` が空だと `pnpm validate` が警告を出す。
3. 下げることを恐れない。この仕組みは数字を伸ばすためではなく、
   **次に何をやるかを決めるため**にある。実態より高い値は、空白を隠して判断を狂わせる。
4. 直したら `pnpm growth snapshot` を実行する。そこが成長の起点になる。

## この初版の限界

棚卸しの価値は、網羅性ではなく「次の行動が決まるか」で測る。初版は
**空白がどこにあるか**（Kubernetes・ネットワーク・RDBMS・性能計測・チームでの実績）
を出すことには成功しているが、**今できることの全量**は表していない。
後者は本人が書き足すしかない。

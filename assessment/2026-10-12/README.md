## 測定の限界

この数字が**測れていないもの**は次のとおり。レベルを見直すときはここを自分で埋める。

1. **業務のコード。** 公開・private を問わず、本人アカウント外のリポジトリは対象外。
   「インフラエンジニア」の職務内容は 1 行も測れていない。
2. **行数は質ではない。** 多ければ上手いわけではなく、少なければ下手でもない。
   行数は「触った量」の目安としてのみ使い、レベルの判定には印（markers）を使った。
3. **AI 協働の寄与。** コミットに AI の署名があるかは測れるが、
   設計のどこを自分で決めたかは測れない。
4. **動いているかどうか。** コードの存在は測れるが、本番で稼働し続けているかは測れない。
5. **検出漏れ。** 命名が想定と違うテスト（例: `test-keybindings.py` は `test_*.py` に
   一致しないため計上されていない）は数に入らない。数字は下振れしている可能性がある。

## 測定で踏んだ罠（同じ測定をやる人向け）

- `git log ... | head -1` は、履歴の長いリポジトリで git に SIGPIPE が飛び、
  `set -o pipefail` + `set -e` で**静かに全体が止まる**。先頭行は `tail -1` で取る。
- `grep -c PATTERN file || echo 0` は、不一致時に grep 自身が `0` を出力した上で
  `echo 0` も走り `"0\n0"` になって算術評価が壊れる。`|| true` を使う。
- `git ls-files` は既定で非 ASCII のパスを `"\343\202\242..."` とエスケープして返す。
  そのまま `[ -f ]` に渡すと常に偽になり、**日本語ディレクトリ配下が丸ごと計測から漏れる**。
  `-c core.quotePath=off` が必要（これで Dockerfile が 0 → 5 件になった）。
- `k6` のような短い語は base64 データに誤マッチする（180 件の偽陽性が出た）。
  `grafana/k6` や `from 'k6` のように文脈を含めて検索する。

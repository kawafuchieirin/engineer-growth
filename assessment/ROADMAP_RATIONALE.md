# このロードマップにした理由（2026-10-17）

`data/goals.yaml` と `data/roadmap.yaml` を、なぜこの形にしたかの記録。
**1 年後に「なぜこうなっていたか」を思い出せないと、見直しの判断ができない。**

## 0. 方向を固定しない設計に変えた（2026-10-17 追記）

聞き取りの直後、本人が**「どう成長するか迷っている」**と述べた。
そこで**方向の固定をやめた**。

迷っている状態で方向を固定すると、精緻な計画を作って実行 0 件になる。
その実例がすでにある（14 資格・18 ヶ月の計画 → 取得 0 件）。
**決めるために必要なのは情報ではなく、試した感触。**

対応は 3 つ。

1. `horizon.vision` を「未決定。2027-03-31 までに 2 つ試して決める」に書き換えた
2. `g-2026q4-choose-direction` を追加した。「決めないことを決める」目標で、
   KR は「2 つ試す」「感触を記録する」「1 つ選ぶ」の 3 つ
3. ロードマップを 2 層に分けた
   - **方向に依存しない**: `m-choose-direction` / `m-postmortem-habit` / `m-first-article`
   - **方向に依存する**: `m-team-mechanism` 以降。`m-choose-direction` に依存させ、日付は仮とした

候補 7 つと試し方は [GROWTH_PATHS.md](./GROWTH_PATHS.md)。

試すのは **A（今の環境で任せられる人）と B（仕組みを作って渡す）**。
同じ 1 手から次の行動が 2 つに分岐するため、比較のコストが最も小さい。

```
ポストモーテムを 1 件書く
        ├─> チームに共有して再発防止の変更を通す      → A の感触
        └─> テンプレート化してチームが使う形にする    → B の感触
```

**2 つ試して決まらないことも結果**として扱う。そのときは候補を入れ替えて延長する。

> 以下の §1 以降は、方向を固定していた時点の設計記録。
> 時間の出どころで軸を分ける考え方（§3）と、入れなかったものの理由（§5）は
> 方向が決まっても変わらないため、そのまま残している。

## 1. 本人が答えた 4 つ（方向は後に未決定へ変更）

ロードマップを作る前に聞き取りをした。**行き先が決まっていない状態で作ると、
わたしがキャリアを決めてしまう**ため、分岐する点だけを確認した。

| | 質問 | 答え |
|---|---|---|
| 1 | 2〜3 年後の行き先 | 今の環境で「任せられる人」になる → **その後「迷っている」と述べ、未決定に変更** |
| 2 | クラウドの軸 | **GCP に広げる** |
| 3 | 「仕組みを作る」強みの扱い | **職務にする（社内に仕組みを入れる）** |
| 4 | 学習と発信に使える時間 | **週 5 時間未満** |

## 2. この 4 つは、そのままでは両立しない

**4 が決定的な制約だった。**

- 週 5 時間未満 = 四半期で約 **60 時間**
- `gcp-cert-master/README.md` の計画は **「週 10 時間・18 ヶ月」**で 14 資格
- 週 5 時間未満で同じことをやると **36 ヶ月**

さらに 1（任せられる人 = level 4 相当）と 3（社内に仕組みを入れる）も
時間を要求する。全部を週 5 時間に詰めると、**計画段階で破綻している**。

> 同じ失敗の実例が既にある。14 資格・18 ヶ月の計画、合格ゲート 6 項目の定義、
> 進捗判定アプリまで作って、**取得は 0 件**。
> 計画の精緻さが実行量を保証しないことは、この人自身のデータが示している。

## 3. 抜け道：時間の出どころで軸を分ける

**「任せられる人になる」は学習時間では達成されない。**

| 行動 | 必要なもの |
|---|---|
| 設計を自分で起こして通す | 業務の**機会**。勉強量ではない |
| 技術選定を主導する | 業務の**機会** |
| 後進を育てる | 業務の**機会** |
| 社内に仕組みを入れる | **既に 5 回作った型の転用**。学習コストはほぼゼロ |
| GCP の資格を取る | **学習枠を消費する** |
| 記事を書く | **学習枠を消費する** |

そこで軸を 4 本に分け、**時間の出どころを明示した**。

| track | 名前 | 時間の出どころ |
|---|---|---|
| `trust` | 任せられる人になる | **業務** |
| `platform` | 仕組みを社内に出す | **業務**（型の転用） |
| `gcp` | Google Cloud | **学習枠** |
| `output` | 発信 | **学習枠** |

**ルール: 学習枠（`gcp` + `output`）のマイルストーンは 1 四半期に 1 つまで。**
60 時間で 2 つ並べると、どちらも終わらない。

## 4. 起点を 1 つに絞った

最初のマイルストーンは **`m-postmortem-habit`（障害対応にポストモーテムを入れる）**。
ここを起点にしたのは、**4 つが同時に埋まる唯一の場所**だから。

| 埋まるもの | 根拠 |
|---|---|
| SRE 信頼性階層の空白 | 監視とインシデント対応は業務で埋まっているのに、その上の 1 段だけが空いている |
| 転職市場で最も弱い点 | 障害面接の「**何を変えたか**」が語れない（`assessment/VIEW_MARKET.md`） |
| やりたいことの 2 番目 | 記事の題材になる。現在 **記事 0 本** |
| level 4 の証跡 | チームに再発防止を通せば「他者への影響」になる |

そして **`/retro` の仕組みは既に自分で作ってある**。道具が揃っていて、
業務の障害にだけ使われていない状態だった。

依存関係もここから引いた。

```
m-postmortem-habit ─┬─> m-first-article      （題材になる）
                    └─> m-team-mechanism     （最初の「社内の仕組み」になる）
                              └─> m-design-lead
                                      └─> m-mentoring
m-gcp-ace ─> m-gcp-next
m-first-article ─> m-output-habit
```

## 5. 意図的に入れなかったもの

| 入れなかったもの | 理由 |
|---|---|
| **Kubernetes** | 求人の必須要件は 12 件中 2 件。週 5 時間未満では費用対効果が悪く、「任せられる人」にも必須ではない |
| **GCP の 3 本目以降** | 1 本目の**実時間を測ってから**決める。計画段階で 14 本並べるのは、取得 0 件だったやり方そのもの |
| **大規模運用（1 万 QPS 等）** | 今の環境では原理的に積めない。行き先を「今の環境で」に決めたため追わない |
| **分散トレーシング / Prometheus** | 800 万円台の求人の一部が要求するが、転職が目的ではないと明言されたため優先度を下げた |
| **AWS の深化** | 12 冠を持ち業務でも使っている。「GCP に広げる」を選んだため、こちらは維持に留める |

## 6. 1 年後に見直すときの判断基準

次のどれかが起きていたら、ロードマップが実態と合っていない。

- **`m-postmortem-habit` が 2026-12-19 を過ぎても `planned` のまま**
  → 業務の中で機会を取れていない。行き先 1 の前提が崩れている
- **`m-gcp-ace` が 2027-03-31 を過ぎても合格していない**
  → 週 5 時間未満という見積りが甘い。学習枠をさらに絞る
- **記事が 1 本も出ていない**
  → 「書く力はある、足りないのは出す先だけ」という読みが間違っていた
- **新しいリポジトリが 3 つ以上増えている**
  → 始める速度が続ける速度を超える傾向が再発している（2026-10 に 6 件新規作成）

## 7. この文書の限界

- 業務の機会（設計を起こす、育成を担当する）が**取れる保証はない**。
  `trust` と `platform` の軸は、本人の意思だけでは完結しない
- 「週 5 時間未満」は自己申告で、実時間は測っていない。
  `m-gcp-ace` で初めて実測が取れる
- 資格管理機能（`data/certifications.yaml`）が進行中で、
  完成すると GCP の進捗が機械的に追えるようになる。
  そのときこのロードマップの `gcp` 軸は書き直す価値がある

## 課題

「自分は何ができて、何ができないのか」を聞かれたときに毎回答えが変わっていた。
評価面談の前に慌てて棚卸しし、終わると忘れる。これが数年続いていた。

問題は記憶や意欲ではなく、**置き場所がない**ことだった。

- スキルの自己評価はスプレッドシート、目標は社内ツール、学びの記録はブログ。
- 三者がつながっていないので「この記事はどのスキルの裏付けになるのか」が追えない。
- 棚卸しの結果が文章なので、半年前との差分が取れない。

## 試したこと

1. **まず Markdown に全部書いた。** 読みやすいが集計できず、
   「レベル 3 以上がいくつあるか」を数えるのに目視が必要だった。
2. **スプレッドシートに移した。** 集計はできるがレビューの差分が読めず、
   変更理由（なぜレベルを上げたのか）が残らなかった。
3. **YAML + Git に落ち着いた。** 事実をデータとして持ち、見せ方は生成物にする。

最終的な構造はこうなった。

```yaml
# data/skills.yaml
skills:
  - id: infra-terraform
    name: Terraform
    category: infrastructure
    level: 3
    evidence:
      - 本番の VPC / ECS を IaC 化し、CI から apply する構成を設計した
    next: モジュール設計とテスト（terraform test）を実務で回す
```

`level` を 0〜5 の数値にしたのが効いた。文章のままでは平均も差分も取れないが、
数値なら「カテゴリ別平均」や「前回との差」が機械的に出る。
レベルの定義自体は `data/levels.yaml` に 1 か所だけ置き、曖昧さを排除した。

| 層 | 置き場所 | 役割 |
|---|---|---|
| データ | `data/*.yaml`, `blog/posts/*.md` | 事実のみを持つ |
| スキーマ | `src/schema/` | zod で構造を検証する |
| モデル | `src/lib/` | 読み込みと集計（純粋関数） |
| レンダラ | `src/render/` | HTML / Markdown を生成する |

## 原因

元の問題は「棚卸しが続かないこと」ではなく、**単一の信頼できる情報源が無いこと**だった。

情報源が 3 つあると、更新のたびに 3 か所を直す必要がある。
人間は 3 か所を同期し続けられないので、やがてどれも信じられなくなり、
結果として「毎回作り直す」という一番高コストな運用に落ちる。

> 同じ事実が 2 か所にあるなら、それは 2 か所とも間違っているということだ。

## 学び

- **事実と見せ方を分ける。** YAML が事実、HTML と `PROFILE.md` は生成物。
  生成物を手で直さないルールにすると、直す場所が自動的に 1 つに決まる。
- **数値にできるものは数値にする。** レベルを 0〜5 にしただけで、
  平均・カテゴリ別の偏り・前回比が計算できるようになった。
- **参照整合性を CI で守る。** 記事の front matter に書いた `skills` が
  `data/skills.yaml` に存在しない場合はビルドを失敗させている。
  これがないと、ID のタイポが「紐付いていないのに紐付いて見える」状態を作る。
- **ブログをスキルの裏付けにする。** 記事に `skills` を書くことで、
  「レベル 3 と主張する根拠はこの 3 本の記事」と言えるようになった。
  逆に、記事が 1 本もないスキルは自己評価が高すぎる可能性が高い、というシグナルにもなる。

次は目標（`data/goals.yaml`）とロードマップを同じ仕組みに載せて、
「今やっていることが、どのスキルのどのレベルに向かっているのか」を一枚で見られるようにする。
